Spec-Driven Development

Write the spec before the code

SDD means writing a structured specification before writing code with AI. The spec becomes the shared source of truth for both the human and the AI agent.

  • Spec-first — a well-thought-out spec is written before AI-assisted development begins
  • Spec-anchored — the spec is kept after the task, used for evolution and maintenance
  • Spec-as-source — the spec is the only artifact humans edit; code is fully generated

Kiro is primarily spec-first. Spec-anchored and spec-as-source are more advanced levels not yet fully addressed by Kiro.

What is a spec?

A structured, behaviour-oriented artifact written in natural language that expresses software functionality and serves as guidance to AI coding agents.

NatWest Virtual Cards SDD Pilot

Specs differ from general context documents (rules files, product descriptions). Those apply across all sessions — specs are scoped to a specific feature or task.

Kiro Overview04 / 14
What Kiro is

Lightweight, spec-first, VS Code-based

Approach
Spec-first
Kiro is the most lightweight of the SDD tools. It focuses on spec-first usage — writing a spec for a task or user story before AI-assisted coding begins. Spec-anchored usage over time is not a primary focus.
Distribution
VS Code extension
Kiro is distributed as a VS Code-based IDE. The three workflow steps are guided directly inside the editor, making the experience feel native and integrated.
Scope
Task, story, or wider orchestration
The IDE workflow is human-in-the-loop by design — one task at a time with developer review. For broader automation, Kiro CLI supports the Ralph Loop: a shell script feeds the three spec files into kiro-cli chat repeatedly, discarding context after each task to prevent degradation — enabling overnight autonomous execution across an entire task list.
Memory bank
Steering files
Kiro calls its memory bank concept “steering”. Default topology: product.md, structure.md, tech.md. Contents are flexible — no specific files are required by the workflow.

The Workflow

Requirements → Design → Tasks — three markdown documents, one guided flow

Kiro Workflow06 / 14
Three-step workflow

Each step is one markdown document

Step 01
Requirements
User Stories in “As a…” format with acceptance criteria in EARS format — WHEN [trigger] THE SYSTEM SHALL [response].
Step 02
Design
A design document covering the technical approach. Structure may vary by task — Kiro generates this based on the requirements. Covers architecture, data models, and implementation approach.
Step 03
Tasks
A list of implementation tasks that trace back to requirement numbers. Each task gets UI controls to run it individually and review the resulting code changes per task.

Kiro Workflow — Requirements07 / 14
Step 01 — Requirements

User stories with EARS acceptance criteria

  • Each requirement is a User Story in “As a …” format
  • Acceptance criteria use EARS format — Easy Approach to Requirements Syntax
  • EARS pattern: WHEN [condition] THE SYSTEM SHALL [behaviour]
  • Requirements are numbered — tasks in step 3 trace back to these numbers
  • Kiro generates this document; the developer reviews and refines it
Acceptance criteria format
User Story
As a developer, I want to configure the service externally, so that I can deploy to different environments without rebuilding.
Acceptance Criteria — EARS Format
WHEN the service starts with an environment variable set
THE SYSTEM SHALL use that value instead of the default

WHEN no environment variable is provided
THE SYSTEM SHALL fall back to the built-in default value
EARS = Easy Approach to Requirements Syntax — unambiguous, testable, traceable

Steering — always-on context

Steering & Skills: persistent knowledge

Steering files are markdown documents that give the AI persistent awareness of your project across every session. They are always loaded — no activation needed.

product.md — what the product is and does
structure.md — how the codebase is organised
tech.md — technology stack and conventions

Steering is Kiro-specific. Supports always, fileMatch, and manual inclusion modes. Use for project standards and team conventions.

Skills — on-demand workflows

Skills are portable instruction packages that load only when needed. They follow the open Agent Skills standard and can be shared across teams and tools.

  • Progressive disclosure — only name & description loaded at startup; full instructions activate on match
  • Invoke explicitly with /skill-name slash command in chat
  • Workspace scope .kiro/skills/ or global ~/.kiro/skills/
  • Can include scripts for deterministic tasks — validation, file generation, API calls
  • Importable from community via GitHub URL
Context Hub — planned addition
Skills can be sourced from the community via Context Hub (chub get author/skill-name). Future plan: also pull Docs on-demand — large API/SDK reference knowledge fetched per-task, without bloating always-on context.

Observations11 / 14
Updated view — Kiro docs + Martin Fowler

Key observations and open questions

Observation Detail
Problem sizing Kiro offers three distinct workflows — Requirements-First, Design-First, and Bugfix Specs — each sized for a different type of problem. No single workflow is forced on every task.
Reviewing markdown With only 3 files per spec, the mental model of requirements → design → tasks is intuitive. Bugfix Specs reduce this further to a single focused bugfix.md, cutting review overhead for fixes.
Spec-anchoring Kiro is primarily spec-first. Spec-anchored usage — maintaining a spec across a feature's lifetime through multiple tasks — is not yet a documented part of the workflow.
Agent compliance Bugfix Specs include property-based tests that verify the bug is reproducible, the fix works, and no regressions are introduced — making agent compliance objectively verifiable rather than assumed.

Summary

Kiro in one paragraph

Kiro is the most lightweight SDD tool available today. Its three-step workflow — Requirements, Design, Tasks — is intuitive and well-structured. The steering concept provides useful persistent context. The main limitations are its spec-first-only focus (no spec-anchoring), verbosity on small tasks, and the universal challenge that AI agents don’t always follow all spec instructions.

Strength
Simple 3-file workflow, intuitive mental model, VS Code-native
Limitation
Spec-first only, no spec-anchoring, overkill for small tasks
Best for
Medium-sized features, greenfield tasks, structured AI-assisted coding
